# PianoLens rectangle internet relay

Milestone B2 only. Android owns the diagnostic playback clock; the browser animates one white rectangle locally on black. No piano, MIDI, microphone or camera code is added. The existing Android music engine, local connection experiment and native DAT fallback are retained.

The glasses open one fixed HTTPS URL and receive an eight-character code. The user enters that code on the phone. No keyboard or long token is needed on glasses. Codes are cryptographically random, single-use and expire after two minutes. After pairing, separate 256-bit role credentials permit reconnect. Session state is in memory, with a six-hour maximum and cleanup after both peers leave. Restarting the service loses pairing. Select on a disconnected glasses page requests a new code if the phone session has been lost.

All public connections use WSS with normal certificate validation. Authentication secrets travel inside encrypted WebSocket messages, never URL queries/fragments. The relay can read commands; this is transport encryption, not end-to-end encryption. It stores no songs, audio, frames, user accounts or database records. Application logs exclude codes, credentials and message bodies. The fixed route accepts only the five diagnostic operations, snapshots, timing probes and acknowledgements. Messages are limited to 4 KiB, roles and room membership are checked, pairing attempts/rates and room counts are bounded, and slow peers are disconnected rather than accumulating frames.

This is a small development service, not an unrestricted public production relay. Its capacity limits can reject connections; process changes require re-pairing. A free Render service has shared usage allowances and can sleep after 15 minutes without incoming traffic. Cold wake can take about one minute. No paid plan is selected. Public-piano offline use remains dependent on a future local communication solution; the relay requires internet. Local animation continues independently of network frame rate, but it freezes when the controller connection is lost.

Local: `npm ci --ignore-scripts`, `npm test`, then `npm start` (port 8787 by default). `/health` returns the build identity only. Exporting for Render copies the canonical `milestone-a/dist/commands.js` and `timing.js` into this service directory; those copies are not independently maintained implementations. Runtime dependencies: `ws` 8.22.0, MIT. Existing shared PianoLens helpers are MIT.

Public deployment must be a Render **Web Service**, not a Static Site. Use root directory `relay`, build `npm ci --ignore-scripts && npm test`, start `npm start`, health path `/health`, Free instance. The existing rectangle Static Site remains unchanged. TLS is terminated by Render; the server binds `0.0.0.0:$PORT`. No environment secrets or database are required.

Direct transport evidence: the user's actual glasses did not connect to Android loopback; detailed browser error is unavailable, so the exact cause is unconfirmed. The phone is using mobile data with no shared Wi-Fi/hotspot, so its private LAN listeners are not a practical currently available route. The reviewed public Meta toolkit/DAT docs did not establish a native companion-to-web bridge. This relay is the authorised fallback for that environment, not a claim that all direct communication is impossible.

References: https://render.com/docs/websocket , https://render.com/docs/free , https://github.com/facebook/meta-wearables-webapp , https://github.com/websockets/ws . Physical-glasses WSS and pairing acceptance remain required even after desktop/emulator tests pass.
